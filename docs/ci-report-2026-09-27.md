## 3. Defect 1 — `gelf.h: No such file or directory` (kernel objtool)

**Failed run:** 36290916933 — *Build the ISO* step, exit code 2 after ~22 min.

**Evidence (job log):**

```
.../build/linux-6.6.30/tools/objtool/include/objtool/elf.h:10:10:
fatal error: gelf.h: No such file or directory
   10 | #include <gelf.h>
compilation terminated.
make[6]: *** [tools/build/Makefile.build:98: .../tools/objtool/arch/x86/special.o] Error 1
make: *** [package/pkg-generic.mk:283: .../linux-6.6.30/.stamp_built] Error 2
```

**Root cause:** the 6.6 kernel builds `objtool` on the host for the ORC
stack unwinder and stack validation, and `objtool` includes `<gelf.h>`
from the host's libelf development files. The current
`ubuntu-22.04` runner image (version `20260920.303.1`) no longer ships the
libelf headers, and the workflow's *Install Buildroot host dependencies*
step did not install `libelf-dev`. Local builds worked only because the
developer machine happened to have libelf installed.

**Fix** (`.github/workflows/build-iso.yml`):

- added `libelf-dev` — provides `/usr/include/gelf.h` for `tools/objtool`;
- added `libssl-dev` — covers `scripts/extract-cert`, which the kernel
  compiles whenever `CONFIG_SYSTEM_TRUSTED_KEYRING` is on (the default);
  leaving it out risks a second, later failure of the same kind.

**Regression protection:** `scripts/ci_agent.py` PATTERNS now recognizes
both signatures (`gelf.h`/libelf and `extract-cert`/OpenSSL) so a repeat
is diagnosed automatically by the ci-agent workflow.

## 4. Defect 2 — `/etc/dropbear` is a symlink; `mkdir -p` aborts target-finalize

**Failed run:** 36300402937 — first run *with* fix 1. The kernel and all
packages built; the build died on the very last step of
`make target-finalize`, 41m34s in:

```
>>> Executing post-build script .../post-build.sh
mkdir: cannot create directory '.../output/target/etc/dropbear': File exists
make: *** [Makefile:754: target-finalize] Error 1
```

**Root cause:** Buildroot's dropbear package installs
`$(TARGET_DIR)/etc/dropbear` as a **symlink** to `/var/run/dropbear`
(see `package/dropbear/dropbear.mk`, `ln -snf /var/run/dropbear
$(TARGET_DIR)/etc/dropbear`), because the SSH host keys are generated
per boot on the tmpfs. GNU `mkdir -p` on a path that exists **as a
symlink** fails with `EEXIST` — unlike a real directory, which it
tolerates. `post-build.sh` ran with `set -e`, so this one `mkdir` killed
the entire 41-minute build after every compile had succeeded.

**Fix** (`rns-router/buildroot-project/board/rns/x86_64/post-build.sh`):
skip the `mkdir -p`/`chmod 700` when `/etc/dropbear` is a symlink and
leave the symlink in place.

**Regression protection:** a new section in
`rns-router/tests/run-tests.sh` builds a fake target tree containing the
same dangling symlink and runs the real `post-build.sh` against it. The
test reproduces the CI failure exactly with the old script (exit 1,
"File exists") and passes now. Suite total: **115 passed, 0 failed**
(was 113 before; +2 new cases). `scripts/ci_agent.py` also learned this
signature.

## 5. Helper files made functional

The two files uploaded to the repo root could not do anything as uploaded:

| Problem | Effect | Fix |
|---|---|---|
| `ci-agent.yml` at repo root | Actions only loads workflows from `.github/workflows/` — the file was never executed | moved to `.github/workflows/ci-agent.yml` |
| workflow ran `python3 scripts/ci_agent.py` | the script was at the repo root → `No such file or directory` on every run | moved to `scripts/ci_agent.py` |
| `permissions: actions: read` | the agent's `deploy`/`watch` commands POST to the workflow-dispatch API, which needs write | set to `actions: write` |
| — | diagnoser did not know either new failure signature | added patterns for both defects above |

Once merged to `main`, the workflow fires automatically after every
completed `build-iso` run and posts a root-cause diagnosis to the run
summary whenever a build fails. It can also be driven by hand:
*Actions → ci-agent → Run workflow* with `check | diagnose | deploy | watch`.
